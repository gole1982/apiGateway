# 日常操作手册（大白话版）

> 涉及安全的判断（信任边界、写隔离、`center_key` 该不该配）以 **[安全模型.md](安全模型.md)** 为权威口径，本文只讲运维动作。

这篇文章只讲一件事：**改完代码后，怎么让本地和远程服务器都用上新版本。**

整个流程就一句话：**本地改好 → 推到 GitHub → 远程跑一条命令**。中间的编译、打包、测试，GitHub 自动帮你做，你不需要管。

---

## 一、日常更新流程（以后每次改代码都这么做）

### 第 1 步：本地改代码 + 测试（在你自己的电脑上）

1. 改代码。
2. 跑测试，确认没改坏：

   ```bash
   go test ./...
   ```

3. 想本地看看效果，直接运行：

   ```bash
   go run ./cmd/gateway
   ```

   或者用 Docker 方式（效果和服务器一致）：

   ```bash
   docker compose up --build
   ```

### 第 2 步：推到 GitHub（把你改好的代码发出去）

```bash
git add .
git commit -m "这次改了什么"
git push
```

推上去之后，GitHub 会自动开始干活（你可以在 GitHub 仓库页面的 **Actions** 标签里看到进度）：

- 自动跑测试 → 通过后
- 自动编译 → 自动打包成 Docker 镜像 → 存到 GitHub 的镜像仓库

**你什么都不用做，等着就行**（一般几分钟）。

### 第 3 步：远程服务器更新（在服务器上执行）

登录服务器，进入项目目录，执行：

```bash
bash update.sh
```

这条命令会自动完成：拉最新代码 → 拉新镜像 → 重启服务。

**就这一条命令，完事。**

#### 想更快？只换二进制（约 6 秒）

如果只是改了 Go 代码（含前端 `dashboard.html`，它是 `go:embed` 编译进二进制的），
不想等拉镜像，可以用 `local-update.sh` —— 它只把新编译的二进制塞进正在运行的
容器，**不重建镜像、不拉取**：

```bash
bash local-update.sh              # 更新本机容器
REMOTE=user@server bash local-update.sh   # 交叉编译后推到远端容器
bash local-update.sh --rollback   # 回滚到上一次备份的二进制
```

耗时对比（实测）：

| 方式 | 耗时 | 适用 |
|------|------|------|
| `bash update.sh`（拉镜像） | 取决于网络 | 服务器日常更新，**推荐** |
| `docker compose build` | 22–38 秒 | 本地验证镜像构建 |
| `bash local-update.sh` | 约 6 秒 | 本地快速迭代；想省掉拉取时 |

脚本会先备份当前二进制（放在宿主机 `bin/gateway.bak`），更新后做健康检查；
**失败会自动回滚**到上一版本。所以即使新版本起不来，服务也不会一直挂着。

> 注意：`local-update.sh` 只换二进制，**不会**改 `proxy.cfg`、compose 配置或
> 环境变量。改了这些配置请用 `docker compose up -d`（必要时 `--build`）。

## 二、第一次在服务器上部署（只做一次）

以后每次更新只需要上面第 3 步，但**第一次**要把项目放到服务器上，并且让服务器能登录 GitHub 的镜像仓库。步骤如下：

1. **把项目克隆到服务器**（需要服务器能访问 GitHub）：

   ```bash
   git clone https://github.com/gole1982/apiGateway.git
   cd apiGateway
   ```

2. **准备配置文件**：把 `proxy.cfg` 放到项目目录里（docker-compose.yml 会用到它）。

3. **让服务器能登录 GitHub 镜像仓库**（只做一次）：

   去 GitHub → 头像 → **Settings → Developer settings → Personal access tokens → Tokens (classic)** → 生成一个新 token，勾选权限 `read:packages`，复制生成的 token。

   然后在服务器上执行（把 `你的GitHub用户名` 和 `你的token` 换成真实的）：

   ```bash
   echo 你的token | docker login ghcr.io -u 你的GitHub用户名 --password-stdin
   ```

   提示 `Login Succeeded` 就成功了。

   > 嫌麻烦的话，也可以把镜像设为公开：GitHub 仓库页面 → **Packages** → 找到 apiGateway 包 → **Package settings** → 把可见性改成 Public。这样服务器不用登录也能拉。但注意：镜像公开等于任何人都能下载你的程序，自己权衡。

4. **启动服务**：

   ```bash
   docker compose up -d
   ```

5. 打开 `http://服务器IP:24680` 确认面板能访问。

## 三、几个你可能关心的问题

### 备份与恢复（重要，建议设成定时任务）

数据在 Docker 卷 `gateway-data` 里的 `gateway.db`（SQLite 单文件）。
备份就是把这个文件复制出来；恢复就是把它复制回去。

**备份**（在服务器上执行）：

```bash
# 确认卷的真实名字（项目名 + 卷名，通常是 apigateway_gateway-data）
docker volume ls | grep gateway-data

# 用 sqlite3 的 .backup 做**一致性**备份。
# 不要直接 cp —— 数据库正在写入时 cp 出来的可能是坏的（半写状态）。
docker run --rm \
  -v apigateway_gateway-data:/data \
  -v "$PWD/backups":/backup \
  alpine:latest \
  sh -c 'sqlite3 /data/gateway.db ".backup /backup/gateway-$(date +%Y%m%d-%H%M%S).db" 2>/dev/null \
    || cp /data/gateway.db /backup/gateway-$(date +%Y%m%d-%H%M%S).db'
```

如果镜像里没有 `sqlite3`（本项目的运行镜像是 alpine，没装），上面的 `||`
兜底会退化成 `cp` —— 那是**不安全**的。推荐改用停机备份：

```bash
# 停机备份：最简单可靠，代价是几秒钟不可用
docker compose stop gateway
cp "$(docker volume inspect apigateway_gateway-data --format '{{ .Mountpoint }}')/gateway.db" \
   "backups/gateway-$(date +%Y%m%d-%H%M%S).db"
docker compose start gateway
```

**恢复**：

```bash
docker compose stop gateway
cp "backups/gateway-20260929-030000.db" \
   "$(docker volume inspect apigateway_gateway-data --format '{{ .Mountpoint }}')/gateway.db"
docker compose start gateway
```

> ⚠️ **恢复后必须用备份当时的那个 `APIGATEWAY_KEY` 启动**，否则数据库里的
> 加密字段（平台 token、Key、Supabase secret）**全部解不开**。密钥不在数据库里，
> 也不在备份里 —— 它在 `.env`。**所以 `.env` 要和数据库备份一起留存。**

**定期清理**：日志表会一直增长（`request_logs` 每次请求一行）。
面板里可以调保留天数；也可以直接删：

```bash
docker compose stop gateway
sqlite3 <卷路径>/gateway.db "DELETE FROM request_logs WHERE timestamp < datetime('now','-90 days');
                         DELETE FROM log_events WHERE request_id NOT IN (SELECT id FROM request_logs);"
docker compose start gateway
```

### 主密钥（APIGATEWAY_KEY）

主密钥**只能来自环境变量 `APIGATEWAY_KEY`**（64 位 hex）。没有它网关**拒绝启动**，
不会像旧版那样"自动生成一把随机 key 写进 `~/.apiGateway.key`"—— 那个行为在容器里
是定时炸弹：文件随容器重建消失，下次启动生成新 key，历史密文集体解不开。

```bash
# 生成一把
openssl rand -hex 32

# 写进 .env（compose 会透传成容器内环境变量）
echo "APIGATEWAY_KEY=<上面那串>" >> .env
```

**从旧版升级**（原本用 `~/.apiGateway.key`）：新版本启动会失败，并在报错里
打印现成的迁移命令（bash 与 PowerShell 各一条），照抄执行即可，历史数据不受影响：

```bash
export APIGATEWAY_KEY=$(cat ~/.apiGateway.key)   # bash/zsh
# PowerShell: $env:APIGATEWAY_KEY = Get-Content "$env:USERPROFILE\.apiGateway.key"
```

确认生效后，旧文件可以删掉（它已不再被读取，留着反而容易误以为还在用）。

### 换密钥（轮换 APIGATEWAY_KEY）会怎样？

主密钥决定全部 `enc:` 密文的可解性。换新密钥后，本地旧密文一律解不开。
**但丢 key 不等于丢配置** —— 分三类看：

| 数据 | 能否恢复 | 怎么恢复 |
|------|---------|---------|
| 平台 token / login_password / Key / 模型 / 接口定义 | ✅ 能 | 从中心（Supabase）重新拉取。`center_key` 留空时中心存**明文**（`proxy.cfg` 里默认就是留空），拉回来后自动用新本地密钥重新加密入库 |
| `settings` 里的中心连接凭据（`sb_api_key` / `sb_center_key`） | ⚠️ 需手工重录 | 它们**不在** bundle 里。丢 key 后无法解密，需去 Supabase 控制台重新复制，在面板「中心配置」页粘一次 |
| 本地遥测（`request_logs` / `rapi_metrics` / `sessions` / 趋势） | ❌ 永久丢失 | 这些从不同步到中心，丢了就是丢了。对账务无影响，只是历史曲线归零 |

所以轮换流程是：

1. 先备份数据库 + **备份当前 `APIGATEWAY_KEY`**（这是唯一的真相来源）；
2. 记下 Supabase 项目 URL 与 secret key（轮换时要用）；
3. 改 `.env` 里的 `APIGATEWAY_KEY`，`docker compose up -d`；
4. 进面板「中心配置」重录 Supabase URL + secret key；
5. 若之前配过 `center_key`，也要一并重录（它也在 settings 里被加密）；
6. 触发一次同步，定义类数据自动回来。

> 本项目**没有**自动重加密工具（`crypto` 包只有单 key 加解密，没有 key ring）。
> 绝大多数场景下你真正要轮换的是**平台侧的 LLM Key**（面板里直接改），零风险；
> 主密钥轮换是很少发生的事，按上面 6 步走即可。

### 数据会丢吗？

不会。程序的数据（数据库、日志）存在 Docker 的卷（`gateway-data`）里，更新镜像、重启服务都不会动它。

> 旧版本曾把数据库写在容器内的 `/app/gateway.db`，该路径不在持久化卷中，容器重建后会丢失。新版本已改为写入 `/app/data/gateway.db`；如果旧版本曾经产生过数据，请先从旧容器/备份复制出来，再启动新版本。

### 更新出问题了怎么办？想退回旧版本？

镜像仓库里保留着每次更新的历史版本。回退就是指定旧版本再启动：

```bash
docker compose pull
docker compose up -d
```

如果只是刚更新完发现有问题，最直接的办法：**在 GitHub 上找到上一次成功的提交，点"回退"**，然后重新 `git pull`，再跑一次 `bash update.sh`。

### 更新后本地和远程版本不一致？

只要你的更新流程是"先 push 再跑 update.sh"，两边就永远一致。以 GitHub 上的代码为准。

### 服务器上怎么看日志、查问题？

```bash
docker compose logs -f gateway
```

### 这套东西在 GitHub 上怎么看到状态？

GitHub 仓库页面 → **Actions** 标签。绿色对勾 = 这次构建成功；红色叉 = 有问题（点进去看哪一步红了）。

## 五、配置中心化（多台机器同步配置，可选）

如果你只在 1 台机器上跑，**不用看这一节**——上面的流程就够了。这一节是给"3 台机器各跑一个实例、想统一管理平台 / key / 模型配置"的场景准备的。设计细节见 [中心 / 管理 / 代理 配置同步设计](superpowers/specs/2026-09-03-center-edge-config-sync-design.md)。

整体是 3 个组件：

- **中心**：一个 Supabase（免费档）Postgres 库，存所有 API 配置 + 一个版本号。
- **管理端**：你自己电脑上额外部署一份带完整面板的程序，录入配置时实时写进中心。
- **代理端**：每台跑转发的机器部署的，定时问中心"版本号变了吗"，变了就把最新配置拉到本地再转发。

### 第 1 次搭建（只做一次）

1. **建 Supabase 项目**（免费）：去 supabase.com 注册 → New project → 在 **Settings > API Keys**（`/dashboard/project/_/settings/api-keys/`）拿到项目 URL 和两个 key：**publishable key**（`sb_publishable_...`，旧称 anon，只读、可放转发机）和 **secret key**（`sb_secret_...`，旧称 service_role，可写、只给你自己，别放到转发机器上）。

2. **建表 + 版本号 + 拉取接口**：在 Supabase 的 **SQL Editor** 跑项目里的 [`scripts/supabase_schema_v2.sql`](../scripts/supabase_schema_v2.sql)（**v2 自然键**：凭据表 `credential` + 绑定表 `endpoint_credential`）。它会建好定义表 + `config_meta.version` + 每次增删改在事务提交时自动 +1 的触发器 + `get_bundle()` 拉取接口。

   > 第 4 步会 `TRUNCATE` 全部 6 张定义表，有显式闸：需在**同一 SQL 会话**里先 `SET apiGateway.destructive = 'yes';` 再整体执行，否则脚本报 `RAISE EXCEPTION` 中止。闸用于防止推送成功后误跑第二遍静默清空数据。

   建完跑 [`scripts/supabase_verify_v2.sql`](../scripts/supabase_verify_v2.sql) 复核（只读，含写隔离校验）。**写隔离是必需项**：v2 脚本第 7 节会启用 RLS 并撤掉 publishable/anon 的写权限；若没生效，publishable key 也能写定义表，程序会把代理端误判成"管理端（可写）"并真的直写中心。旧的 `scripts/supabase_schema.sql` 是 v1 脚本，**不要跑**。**管理端面板已上线**：录入配置直接在面板「平台/密钥/模型/接口」管理页操作（直写中心），不再需要手动 SQL 插入；也可用 [`scripts/supabase_seed_example.sql`](../scripts/supabase_seed_example.sql) 模板批量初始化。详见 [初次配置指南](初次配置指南.md)。

3. **配代理端**（每台转发机器）：`proxy.cfg` 加一段——

   ```ini
   [sync]
   source_url = https://你的项目.supabase.co/rest/v1/rpc/get_bundle
   version_url = https://你的项目.supabase.co/rest/v1/rpc/get_version
   anon_key = 你的 publishable key（sb_publishable_...）  ; 只读，可放转发机
   center_key = 生成一串32字节随机密钥   ; 给 token 加密用，管理端必须配同一串
   poll_interval_sec = 60
   ```

4. **配管理端**（你自己电脑，只需一台）：管理端 = 本机一份带完整面板的程序，面板里加平台、加 key、发现模型，**所有改动实时直写中心**。也可在面板「中心配置」页直接录入 URL+key 自动判定角色（推荐，见 [初次配置指南](初次配置指南.md)）；用 `proxy.cfg` 则配（注意 service_key 用 secret key，别放到转发机器上）——

   ```ini
   [management]
   supabase_url = https://你的项目.supabase.co
   service_key = 你的 secret key（sb_secret_...）  ; 仅管理机，绝不外泄
   center_key = 跟代理端同一串        ; 加密 / 解密 token 用
   ```

   启动后日志出现 `[MGMT] management mode` 即生效。管理机**不需要**再配 `[sync]`（它自己写、自己即时拉回）。

### 日常用（每次改配置都这么做）

1. **配了管理端（推荐）**：在**你自己电脑**启动管理端，打开 `http://localhost:24680` 面板，像以前一样加平台、加 key、发现模型、改路由——所有改动实时直写中心，版本号自动 +1。
2. **没配管理端**：在 Supabase **SQL Editor** 用 `INSERT/UPDATE/DELETE` 改定义表（参照 `scripts/supabase_seed_example.sql` 模板；一段逻辑变更选中整段一起执行）。
3. **你什么都不用做**，各台转发机器会在最多 60 秒（`poll_interval_sec`）内自动拉到新配置并生效；急用可在代理面板点"手动刷新"或调 `POST /api/sync/refresh`。

### 注意

- **同一时间只开一个管理端**：开两个管理端同时改同一平台会冲突（中心会拦重名 / 引用孤儿，但删除和新增交叉不保证）。靠操作纪律，别同时开。
- **中心库必须做写隔离**：v2 脚本第 7 节启用 RLS 并撤掉 publishable/anon 的写权限后，代理端只能读、写会被拒；管理端用 secret key（`BYPASSRLS`）不受影响。没做隔离时 publishable key 会被判成管理端并真的能写中心。
- **publishable key 能读到 token**：publishable key 的准入由人工分发控制（本身不公开、不进前端），所以中心把 token 交给它是设计内行为。但持有它就等于能读全部 token。`center_key`（可选）只防**中心库落库数据被盗**（中心侧泄露 / 只拿到中心库副本、没碰过你的机器时只得到密文）；它**不防**凭据泄露——`center_key` 与 publishable key 同在 `proxy.cfg`，能读到 key 的路径同样能读到它。
- **中心或网络挂了**：转发机器继续用本地缓存的旧配置转发，**不会中断业务**，面板会显示"同步失败"红色告警。等中心恢复，下个周期自动追上。
- **数据不会丢**：配置在中心 Supabase 里；转发机器本地也有缓存副本。中心挂了只是拉不到更新，不影响转发。
- **Supabase 免费档 7 天不活跃会暂停**：日常在用就不会；暂停了也只是拉不到更新，转发照旧。
