# 控制台 UI 信息架构梳理与视觉统一方案（草案 v2）

- 日期：2026-10-31
- 状态：待评审（未实施）
- 范围：`internal/service/dashboard.html`（单文件内联 Vue，含全部样式、模板与逻辑）
- 触发：排查管理端主页面「需要往下滚一截」时，发现顶栏/侧栏存在信息架构与视觉语言不一致
- 变更：v2 依据 2026-10-31 的需求方决策，收敛 §3 归位、新增向导与刷新定义

---

## 0. 结论摘要

**不需要推翻重做 UI。** 做一轮「归位 + 统一 + 向导化新增」：

1. **信息架构归位**：顶栏右侧 = 被动状态 / 通知；主动操作下沉或向导化。
2. **视觉语言统一**：功能图标一律线性 SVG；剔除 emoji；图标按钮同规格。
3. **新增向导化**：`＋新增` 重定义为**向导**，直接编排各操作界面的新增流程；每个新增界面内加「下一步」，把刚建的对象透传给下一步。
4. **补齐模型新增**：模型管理页目前无独立新增入口，需补。
5. **刷新保留在顶栏**，且升级为 3 项功能入口。

已单独修复的真 bug（§1.3）与本方案解耦。

## 2. 设计原则

| 编号 | 原则 | 含义 |
|------|------|------|
| P1 | 顶栏右侧 = **被动** | 状态 / 通知类；用户被动点击查看 |
| P2 | 左侧栏 = **主动导航** | 模块入口 |
| P3 | 内容区 = **主动操作** | 新增 / 刷新 / 过滤，跟随页面 |
| P4 | 单一视觉语言 | 线性 SVG；禁 emoji 充当功能图标；同层级按钮规格一致 |
| P5 | **例外：刷新** | 刷新是全局运维动作，**特例保留在顶栏**（§4.2） |

## 3. 顶栏元素归位

| 元素 | 性质 | 归位 | 说明 |
|------|------|------|------|
| 未读信息 | 被动提示 | **留顶栏** | emoji 🔔 → 线性 SVG 铃铛 |
| 中心同步状态 | 被动状态 | **留顶栏** | emoji ☁ → 线性 SVG；异常保留红点 |
| 版本更新 | 被动提示 | **留顶栏** | 八角猫 → 线性「下载/升级」图标；GitHub 链接留在展开面板 |
| 代理端口状态 | 被动状态 | **新增到顶栏** | 由侧栏底部搬入；绿=在线 / 红=离线 |
| 刷新 | 全局运维 | **留顶栏（例外）** | 升级为 3 功能入口（§4.2） |
| ＋新增 | 主动（向导） | **重定义为向导** | 编排各页新增，见 §5 |

## 4. 顶栏终态

### 4.1 右侧元素（右起）

```
[端口状态] [刷新▾] [未读] [同步] [更新]
```

### 4.2 刷新（3 功能）

顶栏刷新由单动作改为**可展开菜单**，含 3 项：

1. **中心侧刷新**
2. **端侧刷新**
3. **中心侧与端侧比较**

**语义（已定，读法 C —— 两侧各自拉取 + 比较，不向中心推送）：**

| 动作 | 语义 | 对应现有实现 |
|------|------|------------|
| 中心侧刷新 | 拉取中心最新定义到本地 | `manualPull`（中心→本地） |
| 端侧刷新 | 拉取端侧（本地）当前状态 | 重读本地镜像 / 统计 |
| 中心侧与端侧比较 | 两侧差异对比（**只读**） | 「同步状态」表 + 差异 |

> 本菜单**不含「本地→中心推送」**——那是对中心的破坏性写操作（现有提示已注明「会用本地定义整体覆盖中心」），不应藏在「刷新」下面。

## 5. 「＋新增」= 向导（重定义）

### 5.1 定位

- 顶栏原「＋新增」（打开独立向导弹窗）**重定义为编排器**：不再维护一套独立的表单，而是**直接对接各操作界面已有的新增界面**。
- 向导流程按依赖顺序串起各页新增：`平台 → 密钥 → 模型 → 测试 → 保存`（沿用现有 `openAddWizard` 的步骤意图，L3686）。
- **入口位置：从顶栏移到「仪表盘」页首**（理由与风险见 §9.1）。

### 5.2 「下一步」透传

- 在**每个新增界面**（添加平台 / 添加密钥 / 新增模型 / 创建接口）内，增加一个 **「下一步」** 按钮；
- 语义：保存当前新增对象 → 打开**下一步**对应的新增界面，并**预填/预选刚刚创建的对象**（如：新建平台 → 下一步 → 添加密钥，且平台已选中）。
- 形成可断可续的链：用户可中途关闭，也可只做单步（等于原有单页新增）。

### 5.3 补齐模型新增

- 模型管理页头补 `+ 新增模型`（`openRapiModal(null)`），与平台/密钥/接口页头对齐；
- 使其既能独立新增，也能作为向导链路中的一环被「下一步」调用。

## 9. 决策记录（2026-10-31 已定调）

| 项 | 决策 |
|----|------|
| ＋新增 | **重定义为向导**，直接对接各操作界面的新增；不再独立维护表单（§5） |
| 各新增界面 | **新增「下一步」**，把本界面新建对象透传给下一步（§5.2） |
| 模型新增 | **补齐**模型管理页的独立新增入口（§5.3） |
| 刷新位置 | **保留在顶栏右上角**（P5 例外） |
| 刷新功能 | 升级为 **3 项：中心侧刷新 / 端侧刷新 / 中心侧与端侧比较**；语义取**读法 C（两侧各自拉取 + 比较，不推中心）**（§4.2） |
| 向导入口 | 从顶栏**移到「仪表盘」页首**（§5.1、§9.1） |

### 9.1 设计意见：向导入口放「仪表盘」页首合理吗？

**结论：合理，但要加限定，否则可能重蹈「把两类东西塞一处」的覆辙。**

支持的理由：
- 仪表盘本就是「总览 + 起手」页，也是默认落地页，作为**端到端配置引导**的入口，可发现性最好。
- 向导流程是 `平台→密钥→模型→测试`，本质是**跨实体的首次配置**，放监控总览页比放顶栏更贴合语义。

需要注意的（建议一并采纳）：
1. **明确分工，避免三个「新增」入口打架**：仪表盘向导 = 端到端引导（建链路）；各列表页 `+ 添加X` = 单点日常新增；两者用文案区分（如仪表盘叫「从零配置向导 / 新建链路」，列表页叫「+ 添加平台」）。
2. **建议条件化显示**：首次使用 / 无任何平台时，仪表盘页首突出显示；已有配置时降级为次要按钮，避免在一个只读监控页上长期放主 CTA。
3. **别与页内既有块抢焦**：仪表盘页首已有「中心连接信息」卡，向导 CTA 应放在标题行右侧（次要视觉权重），不要另起一张大卡。

> 如果你更想要「一个显眼、随时随地可点」的创建入口，代价只能是把它留回顶栏（违反 P1）——两者不能兼得。

## 10. 风险与回归

- 回归面：顶栏宽度、小屏（<1100px）、各列表页页头、各新增弹窗、向导链路。
- 不改逻辑原则：除「下一步」透传与刷新菜单外，不动既有接口调用与数据契约。
- 主内容区超出一屏（待处理 25 项时 579px）属独立议题，本方案不含。
