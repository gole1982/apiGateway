# 安全模型（信任边界 / 写隔离 / token 保密）

本文是**权威口径**。讨论角色判定、写隔离、token 保密时以本文为准，不要在别处重新推导。
相关实现：`internal/service/sbconfig.go`（角色探测）、`internal/db/bundle_apply.go`（同步落库）、
`scripts/supabase_schema_v2.sql` 第 7 节（中心侧 DDL）、`scripts/supabase_verify_v2.sql` 第 10~12 节（校验）。

---

## 1. 信任边界 = 「key 是否由运维者颁发」

系统的准入控制**不是**一套身份/角色体系，而是**分发 key 这个动作本身**：

- 没拿到 key 的机器 → 跑**独立模式**，只读本地 SQLite，不与中心交互，读不到任何 token。**不在威胁面内。**
- 拿到 key 的机器 → 由运维者亲手颁发，**按定义就在信任边界内**。

推论：**"不可信的代理机"是个自相矛盾的词**。能读 token 的机器都持有颁发的 key；没 key 的机器什么都读不到。
所以判断威胁时，轴不是「机器可不可信」，而是「**key 有没有落到不是运维者部署的环境**」。

---

## 2. 三种角色由 key 的**权限**体现，不由配置段名决定

| 角色 | key | 中心侧权限 | 行为 |
|------|-----|-----------|------|
| 管理端 | `sb_secret_…`（旧称 service_role） | 可写（`BYPASSRLS`） | 定义类增删改**直写中心** |
| 代理端 | `sb_publishable_…`（旧称 anon） | 只读 | 轮询版本号，变了才全量拉取 |
| 独立模式 | 无 key / 连不上 | 无 | 纯本地 SQLite |

角色判定 = **无副作用写探测** `PATCH /rest/v1/platform?id=eq.-1`：

| 探测结果 | 判定 |
|---------|------|
| 200 / 204（写成功） | 管理端 |
| 401 / 403（写被拒） | 代理端 |
| 连不上 | 独立模式 |
| 404 / 5xx | 代理端 + 诊断错误（不确认可写，以安全侧为准） |

**意图 vs 事实交叉校验**：若 `sb_publishable_` 前缀的 key 竟然写成功，说明中心库没做写隔离。
此时返回 **代理端 + 显式报错**，绝不静默激活管理端（否则 publishable key 会直写中心）。
旧式 `anon`/`service_role` JWT 无前缀，无法据此判断，只能依赖探测结果。

---

## 3. 写隔离（中心 RLS）—— 职责与边界

**它只落实「publishable = 只读、secret = 可写」这条权限约定，不承担准入。**
准入由运维者人工分发 key 控制（见 §1）。这与"不做 RBAC"完全一致：两者不冲突，是两件事。

DDL 见 `scripts/supabase_schema_v2.sql` 第 7 节：`ENABLE ROW LEVEL SECURITY` + 只读策略 +
`REVOKE INSERT/UPDATE/DELETE/TRUNCATE ... FROM anon, authenticated`；`service_role` 靠 `BYPASSRLS` 保留全权。
用 `supabase_verify_v2.sql` 第 10~12 节复核（只读）。

**为什么必需**：它是角色判定的依据。中心不做写隔离时，publishable 的写探测会成功，
程序会把代理端误判成管理端并**真的直写中心**——这是历史 bug 的根因。

注意：RLS 是**写隔离**，不是身份层；不要把它理解成在引入权限体系。

---

## 4. 为什么不做 RBAC

因为准入靠 key 分发（§1），系统里没有身份概念——没有用户、没有登录、没有角色表。
中心侧只有两种 key 权限（只读 / 可写），这已经足够表达「代理 / 管理」两个角色。
再加 RBAC 是在没有身份层的地基上盖楼：没有主体可以授予角色。

---

## 5. 中心 token 存明文（center_key 已取消）

历史版本曾有 `center_key`（应用层加密，中心存密文 token），现已取消设定，
中心 token 一律存明文。取消的理由正是下面这套论证——保留它只增加运维负担，
不增加实际安全性：

- 它**只防「中心库落库数据被盗」**——中心侧泄露，或有人只拿到中心库副本却
  **没碰过任何一台运维者的机器**，此时对方只得到密文。
- 它**不防凭据泄露**：`center_key` 与 publishable key **同在 `proxy.cfg`**，
  能读到 key 的路径同样能读到它。「用 center_key 兜底 key 泄露」是**循环论证**：

  > 类比 RSA：用**同目录下的另一个 key** 加密私钥，等于没加密——能偷到私钥的路径也能偷到那个 key。
  > 加密私钥只有用**不同信任域**的包裹密钥（例如你脑子里的口令）才有意义。

- 它也**不防「已部署机器被攻破」**：解密材料就在那台机上。

中心库落库数据的静态保护（磁盘加密、备份加密、平台侧访问控制）是 **Supabase 的责任**，
不是本项目的。历史中心若残留 `enc:` 密文，网关会明确报错（不再静默透传），
操作员用「本地到中心」整体覆盖推送把中心改写为明文即可。

---

## 6. 威胁模型一览

| 攻击者拿到 | 后果 |
|-----------|------|
| 什么都没拿到（外部） | 无 |
| 只拿到**中心库副本**，没碰过运维者的机器 | token 明文（Supabase 平台侧保护负责兜底） |
| 运维者部署的某台机器（含配置文件） | token 明文 |
| 某台机器上的 publishable key | 能读全部 token |
| 无 key | 读不到 |

---

## 7. token 可被 publishable key 读取——是设计内行为

`get_bundle()` 与 `credential` 表会把 token 交给任何持有 publishable key 的客户端。
这是**有意为之**：代理端转发请求时必须拿到 token，否则无法工作。
（平台控制台密码与计费网址字段已删除，不在同步范围内。）

因此 publishable key 在语义上**等价于「全部上游 token 的钥匙」**——Supabase 叫它 "publishable"，
但在本架构里它是**服务端高价值密钥**，不是可塞进前端的东西。**不进前端、不进仓库、泄露即轮换。**

---

## 8. 决策清单（照着答即可，不必重新推导）

1. **中心库做写隔离了吗？** → 必须做（§3）。没做则 publishable 会被误判成管理端。
2. **publishable key 怎么管？** → 当高价值密钥管（§7），因为它等价于全部 token 的钥匙。
3. **需要 RBAC 吗？** → 不需要，没有身份层可依附（§4）。
